# CampusMate 工程流程与面试深挖日志

**使用规则：** 本文不是项目宣传稿，而是用于你真正理解业务和应对面试追问的工程日志。每次新增、修改或修复功能时，都要新增一条记录：说明业务为什么需要它、数据如何流动、最可能出什么问题、实际如何验证、以及面试官可以如何追问。

## 0. 用一句话讲完整业务流程

用户先在公开商城发现演示商品；登录后才能创建模拟订单。订单进入以 OAuth 会话隔离的个人空间，用户可以在订单页、个人中心或 AI 客服中查询自己的记录。客服对规则问题先检索公开来源改写的知识库，对商品与订单问题调用受控服务端工具；当证据不足或用户主动转人工时，系统不伪造答案，而是允许登录用户保存只属于自己的模拟工单。管理员负责商品、知识库与固定评测，评测记录用于验证关键链路而不是制造漂亮分数。

完整的页面、数据表、索引状态机、失败分支和面试问答见 [`docs/end-to-end-business-flow.md`](./end-to-end-business-flow.md)。每次新增业务模块时，应先更新该总览，再将工程细节写入本文对应章节。

## 0.1 内联全流程业务、数据与失败响应清单

| 阶段 | 页面或动作 | 核心写入/读取 | 失败响应与面试要点 |
|---|---|---|---|
| 公开发现 | 首页、全部商品、搜索、详情页。 | 读取公开 `products`、`categories`、`productImages`。 | 不要求登录且不承诺真实交易；问“为何公开”时说明商品目录不含订单个人数据。 |
| OAuth 与模拟下单 | 登录后从详情页下单。 | 以会话用户 ID 写入 `orders`、`orderItems` 快照、商品 `reserved` 状态与审计。 | 非 active 商品或未登录被拒绝；问“并发”时说明当前事务和未来条件更新/乐观锁方案。 |
| 本人空间 | 我的订单、个人中心。 | 订单按会话 ID，发布物品按 `sellerUserId` 过滤。 | 他人订单 ID 直接请求也被拒绝并审计；问“为什么不用前端隐藏”时强调服务端所有权判断。 |
| 公开规则客服 | AI 客服政策问题。 | Node 只发送问题文本至 FastAPI；LangGraph → Chroma/BGE 返回公开引用，Node 生成受控回答。 | 无证据转人工；sidecar/BGE 不可用时 TF-IDF 回退，不能泄露身份或订单。 |
| 商品/订单客服工具 | 问商品或“我的订单”。 | Node 执行商品公开检索，或经 OAuth 后执行本人订单工具。 | Python 没有数据库和 Cookie；未登录订单查询返回登录提示。 |
| 模拟人工转接 | 用户主动转人工或无匹配。 | 受保护路由写入 `supportTickets`、工作流轨迹和审计。 | 仅本人读取，不联系真实客服；问“为何保存轨迹”时解释交接、审计和复现价值。 |
| 管理规则与索引运维 | 管理员上传 `.md/.txt`、HTTPS 来源、同步状态、版本替换、失效与批量重建。 | 对象存储/MySQL 是事实源；Node 写分块、指纹和生命周期，Python Chroma 按指纹 upsert/delete 公开规则。 | 索引失败显示 `failed` 并可重试；新版本先同步、旧版本后失效；问“为何分状态”时区分“已上传”“已同步”和“当前可引用”。 |
| 固定评测与复盘 | 管理员运行六类案例、查看项目说明。 | `evaluationRuns` 保存实际意图、引用、拒答和延迟。 | 指标不是 SLA；问“如何防回归”时说明固定输入、预期结果、自动化测试和审计证据。 |

```text
公开商品浏览
  → OAuth 登录
  → 模拟下单（订单快照 + 商品预留 + 审计）
  → 本人订单 / 个人中心
  → AI 客服：意图 → 检索或受控工具 → 引用回答 / 拒答转人工
  → 模拟工单（仅当前会话可见）
  → 管理员知识库与固定评测
```

## 1. 商城发现与模拟下单

| 维度 | 记录 |
|---|---|
| 业务问题 | 校园二手用户需要先通过商品、分类、关键词和详情判断物品是否值得进一步联系，而不应被登录门槛阻断公开浏览。 |
| 用户路径 | 首页/全部商品 → 搜索或筛选 → 商品详情 → 登录 → 创建模拟订单 → 我的订单。 |
| 数据流 | `products`、`categories`、`productImages` 提供公开目录；下单创建 `orders` 与 `orderItems` 快照，并将商品状态改为 `reserved`。 |
| 安全边界 | 创建订单由服务端会话的 `ctx.user.id` 决定，不接收客户端指定买家 ID；非 `active` 商品拒绝下单。 |
| 常见问题 | 两个用户同时对同一商品下单可能产生竞争；演示版依赖状态判断，生产环境应使用事务内带条件更新或乐观锁保证只预留一次。 |
| 当前应对 | 下单写入订单、订单项和商品预留状态处于同一数据库事务；商品不再为 `active` 时会拒绝后续请求。 |

> **面试追问：为什么订单要保存商品标题和价格快照？**  
> 因为商品本身后续可能下架、改名或价格调整；订单必须保留创建时的交易语义，不能每次展示时重新读取当前商品字段。

## 2. OAuth、订单所有权与追加式审计

| 维度 | 记录 |
|---|---|
| 业务问题 | 二手交易最敏感的数据是订单。前端隐藏“别人的订单”无法阻止直接请求 API，因此必须在服务端验证所有权。 |
| 用户路径 | 登录后查看订单列表 → 点击详情 → AI 查询“我的订单”。 |
| 数据流 | Manus OAuth 生成会话；tRPC 上下文提供当前用户；订单读取以 `orders.userId` 与当前用户 ID 比较；审计写入 `auditLogs`。 |
| 安全边界 | `protectedProcedure` 阻止匿名读取；`getOrderForActor` 通过所有权决策拒绝跨账户请求；允许和拒绝路径均有审计事件。 |
| 常见问题 | 受管 TiDB 不支持触发器，无法用数据库 trigger 强制审计；若只靠前端限制，越权请求仍可能读取数据。 |
| 当前应对 | 审计日志只暴露应用层追加写入路径，禁止更新/删除；核心订单读取流程统一经过审计封装，并由测试覆盖允许和拒绝分支。 |

> **面试追问：为什么不让客户端传一个 `userId`，服务端再比对？**  
> 客户端参数本身是不可信输入。最安全的做法是从已验证的会话中取身份，再把它作为查询条件；这样攻击者即使篡改请求体，也无法指定另一位用户。

## 3. 知识库处理与可引用 RAG

| 维度 | 记录 |
|---|---|
| 业务问题 | 交易规则、售后说明和安全 FAQ 分散在文档中。客服若仅靠模型记忆回答，既不能解释来源，也容易把演示规则说成正式平台政策。 |
| 用户路径 | 管理员初始化或上传 Markdown/TXT → 文档处理为知识块 → 用户问规则问题 → 页面展示回答和公开来源。 |
| 数据流 | `knowledgeDocuments` 保存元数据和来源；`knowledgeChunks` 保存内容、来源标签与词项向量 JSON；检索结果带文档 ID、分数和 URL。 |
| 当前算法 | 文本按段落聚合为确定性分块；使用语料级 TF-IDF 和余弦相似度召回 Top-3。检索有分数但不等于语义 Embedding。 |
| 常见问题 | 关键词重叠可能造成伪相关；文档太短、来源不可访问或分块过大都会降低检索质量。 |
| 当前应对 | 罕见词 IDF 测试、无关问题拒答测试、来源 URL 展示与低置信转人工；文档上传限制格式与长度。 |

> **面试追问：为什么不用模型直接回答？**  
> 模型负责压缩和表达，不负责决定事实。检索阈值和引用返回由程序控制，低置信时必须拒答；这样才能解释“依据是什么”和“为什么不回答”。

> **面试追问：TF-IDF 的局限是什么？**  
> 它依赖词面匹配，近义表达与复杂语义理解较弱；当前选择它是为了零外部向量服务、可复现和便于演示。后续可保持文档、引用和阈值接口不变，替换为 Embedding + 向量库。

## 4. AI 客服 Agent 与受控工具

| 维度 | 记录 |
|---|---|
| 业务问题 | “客服”不能只回答规则，还需要在安全前提下找商品、查询本人订单并将无法处理的问题转人工。 |
| 工作流 | 接收问题 → 规则意图分类 → 选择知识检索/商品检索/本人订单/人工转接 → 返回回答、引用、工作流轨迹和工具结果。 |
| 当前工具 | `knowledge_search`、`product_search`、`own_order_lookup`、`handoff_advice`。工具均由 TypeScript 服务端显式调用。 |
| 当前实现边界 | 这是显式状态工作流，不是 LangGraph；也是受控业务工具调用，不是大模型原生 Function Calling。 |
| 常见问题 | 如果将订单工具直接暴露给模型，模型或提示注入可能诱导工具传入其他订单 ID；如果错误处理不当，LLM 不可用会导致客服完全不可用。 |
| 当前应对 | 订单工具只接收会话身份，所有权校验在业务层；规则回答有检索证据 fallback，即使模型暂不可用也会返回基于证据的安全摘要。 |

> **面试追问：Agent 的状态在哪里？**  
> 当前每次请求构造一个显式状态对象，以“接收、意图、工具、回答、转人工”步骤数组返回前端并可保存到工单。这使单轮决策可解释；若要支持长期多轮记忆或恢复，需要新增会话表和持久化状态机。

> **面试追问：为什么 `ask` 可以匿名调用，而订单工具不能？**  
> 公开规则和商品目录没有个人敏感性，所以允许匿名体验；一旦路由到订单工具，缺少会话会被阻止，并返回登录说明，不会执行订单查询。

## 5. 模拟人工工单

| 维度 | 记录 |
|---|---|
| 业务问题 | “转人工”若只是一句文案，无法展示交接信息如何沉淀，也不能体现工单的权限模型。 |
| 用户路径 | 无匹配规则或主动请求人工 → 客服生成转人工工作流 → 登录用户点击创建模拟工单 → 我的模拟工单显示记录。 |
| 数据流 | `supportTickets` 保存当前用户 ID、分类、原问题、回答摘要、工作流轨迹、状态和演示标识；创建/查询追加审计日志。 |
| 安全边界 | 创建和查询使用 `protectedProcedure`；列表查询固定 `where userId = ctx.user.id`，客户端没有指定目标用户的入口。 |
| 常见问题 | 若工单摘要包含模型自由生成内容，可能出现误导；若管理员工单处理没有角色校验，会造成泄露。 |
| 当前应对 | 当前仅保存客服已返回的演示摘要，明确标记不联系真实客服；管理员处理队列尚未实现，不能声称有真实客服系统。 |

> **面试追问：为什么把工作流轨迹也保存到工单？**  
> 转接人员需要知道用户问了什么、系统尝试了哪些工具、为什么没有直接回答。保存轨迹可以减少重复问询，也便于审计模型/检索失败分支。

## 6. 个人中心、管理员后台与固定评测

| 模块 | 业务价值 | 常见问题与应对 |
|---|---|---|
| 个人中心 | 将订单轨迹和已发布物品放入同一用户空间，让演示从“浏览”走到“个人业务状态”。 | `sellerUserId` 是后加字段，历史演示目录缺少归属；当前以管理员账户为演示目录归属并只按字段查询，普通用户保持空态隔离。 |
| 管理后台 | 管理员可维护商品、初始化知识库与上传规则文档。 | 前端不展示入口不足以安全；服务端 `adminProcedure` 对直接请求也返回 `FORBIDDEN`。 |
| 固定评测 | 将规则、无匹配、商品、本人订单、跨账户订单、人工转接 6 类案例写入数据库并记录实际运行。 | 评测指标不等于生产 SLA；当前延迟为本次服务端运行时间，应明确注明采样边界。 |

> **面试追问：为什么要用固定案例，而不是只演示几句提问？**  
> 临时演示不可复现，容易挑选对系统有利的问题。固定案例使预期意图、引用、拒答与延迟都有可追溯基线，变更后可以发现回归。

## 7. 已发生问题与工程处理记录

| 事件 | 原因判断 | 处理方式 | 可迁移经验 |
|---|---|---|---|
| 个人中心的演示商品没有归属 | 早期商品表没有 `sellerUserId`，种子数据也早于该字段。 | 增加迁移、索引和按当前用户查询；对无归属演示商品安全地归属到演示管理员。 | 数据模型演进必须考虑历史数据的兼容策略。 |
| 工单模拟功能缺少数据闭环 | 早期“转人工”只返回文本，不可追踪也无法展示隔离。 | 新建 `supportTickets`、受保护 API、审计和集成测试。 | 每个业务“下一步”都应有数据实体与权限规则，而不只是 UI 文案。 |
| 固定评测扩展后测试失败 | 新增人工转接案例后，旧测试仍断言 5 个案例。 | 同步更新案例计数断言并重跑全套测试。 | 改变评测数据集本身就是行为变更，测试的期望集也必须版本化。 |
| 生成构建出现大包警告 | Mermaid/高亮相关依赖使部分 bundle 超过警告阈值。 | 当前构建成功，记录警告但不伪称性能已优化。 | 性能主张必须区分构建通过、HTTP 响应与真实浏览器体验。 |
| 首次 Python Agent 请求走 Node 回退 | Node 按需启动 FastAPI 子进程，首个 1.8 秒窗口内 sidecar 尚未就绪。 | Node 立即使用已有 TF-IDF 受控回退；FastAPI 就绪后再次请求确认进入 LangGraph/Chroma 轨迹。 | 跨服务冷启动必须设计可解释、安全的退化路径，不能因依赖未就绪放宽权限。 |
| 跨服务手工验证不足 | 首轮仅通过 curl 确认 Node 到 FastAPI 的真实请求，无法作为持续回归证据。 | 新增 `pythonAgentGateway.integration.test.ts`，mock FastAPI 结果并断言仅转发公开消息、匿名订单仍由 Node 拦截。 | 手工运行证明“现在可用”，自动化测试才能证明“下次改动仍安全”。 |
| 项目说明页验证首次出现 404 | 视觉验证误用了 `/project-guide`，实际路由注册为 `/project`。 | 回查路由表后使用真实路径重测，确认六层跨运行时架构卡片可读。 | 测试路径也是接口契约；UI 验证失败先核对路由注册而非盲目修改页面。 |

## 9. 已实现：Python FastAPI + LangGraph + Chroma Agent 服务

| 项目 | 实际结果、问题与应对 |
|---|---|
| 业务目的 | 将“意图路由与规则检索”迁移为真实 Python Agent 服务，同时保留现有 Node 业务网关对订单和工单的最小权限控制。 |
| 实际路由 | FastAPI 仅接收公开用户问题，LangGraph 返回意图与 Chroma 规则证据；Node 根据可信 OAuth 会话决定是否执行商品、本人订单或工单工具。匿名“我的订单”请求已验证为 Node 登录提示，Python 工作流明确记录不访问个人数据。 |
| 实际问题 | 第一次跨服务请求在 Python sidecar 尚未启动时触发 Node 的 TF-IDF 回退；启动日志确认 FastAPI 约随后就绪，第二次请求进入 FastAPI → LangGraph → Chroma 轨迹。 |
| 当前应对 | Python 只绑定 localhost；Node 保留会话、LLM 密钥和个人数据工具；演示知识库从受版本控制的公开语料重建；1.8 秒超时与 TF-IDF 回退保证依赖启动失败时仍不泄露或阻塞个人工具。 |

> **面试追问：为什么不让 FastAPI 直接连 MySQL 并查订单？**  
> 因为订单权限已经在 Node/tRPC 与 OAuth 上下文中经过验证。把数据库凭据和订单读取能力复制到新服务会扩大攻击面；编排服务只做它必要的路由和检索，个人工具继续经过已有网关。

> **面试追问：首次请求如果 Python Agent 没准备好怎么办？**  
> Node 网关为 Python 路由设置短超时；服务未就绪时调用已测试的 TF-IDF 受控回退，绝不把会话或订单数据交给 Python。服务就绪后，后续公开规则请求显示 FastAPI、LangGraph 和 Chroma 的工作流轨迹。

## 10. 已实现：预训练中文 Embedding 检索升级

| 维度 | 实际结果、问题与应对 |
|---|---|
| 业务目的 | 规则咨询中存在“仿制品/侵权”“瑕疵/配件”等词面不完全一致的表达，仅靠哈希或词项重叠会出现伪相关或漏召回。 |
| 模型与运行时 | 选择 MIT 许可的 `BAAI/bge-small-zh-v1.5`，通过 FastEmbed ONNX CPU 加载 512 维预训练中文语义向量。FastEmbed 支持列表将其标为中文模型、约 0.090GB 优化包，避免在双运行时容器中额外加载 PyTorch。 |
| 数据流 | 公开规则文档以 260 字符、48 字符重叠切块；FastEmbed 同时编码 Chroma 文档向量与查询向量。Python 服务只返回公开证据；Node 保留会话、订单、工单、LLM 密钥和 TF-IDF 回退。 |
| 对比证据 | 固定 5 条中文同义改写案例中，BGE Top-1 命中 4/5，旧哈希基线命中 3/5。该小型演示集只说明当前语料上的可复现差异，不等同于生产准确率或通用基准。 |
| 实际问题 | FastAPI sidecar 的首个请求可能尚未完成模型加载或进程启动，因此 Node 首次请求会安全回退到 TF-IDF；服务就绪后再次请求会显示 BGE 工作流轨迹。 |
| 构建期问题 | 在开发服务器、BGE sidecar 与前端生产构建同时运行时，首次 `vite build` 因内存压力以退出码 143 终止。 |
| 当前应对 | Docker 构建期执行模型预热；Python 仅保留一个 CPU 模型实例和短文本批次；本地构建前停止可按需重启的 sidecar，并将 Node 构建堆限制为 1280 MiB 后成功完成。模型加载失败时回退到 512 维哈希向量并在健康端点和工作流中暴露后端状态。 |

> **面试追问：为什么不用更大的 Embedding 模型？**  
> 这是作品集的受限运行时决策。当前部署是 Node 与 Python 共存的 autoscale 容器，优先保证首次启动、内存占用和可回退性。BGE small 中文模型能覆盖当前规则语料；若未来有独立 GPU/更高内存服务，再用离线评测选择更大模型，而不是只因参数更多就替换。

> **面试追问：你如何证明 Embedding 确实更好？**  
> 我没有直接声称通用准确率提升，而是维护固定的中文同义改写检索集：在当前 5 条公开演示规则查询上，BGE 是 4/5，哈希是 3/5。下一步会扩展标注集并加入 Recall@K、MRR 和人工评审，避免小样本过拟合结论。

> **面试追问：预训练模型会带来什么部署问题？**  
> 模型包、ONNX 推理、Python sidecar 与 Node 构建会竞争受限内存。实际开发构建中曾出现退出码 143，所以我选择 FastEmbed ONNX 的 small 中文模型、Docker 构建期预热、单实例 CPU 推理，并让 Node 具备 TF-IDF 回退。若生产内存持续紧张，应将 Embedding 服务迁移到独立的更高内存运行时，而不是取消安全回退。

## 11. 已实现：管理员规则文档增量同步到 Chroma

| 维度 | 实际结果、问题与应对 |
|---|---|
| 业务目的 | 管理员新增规则后，若只写对象存储和 MySQL，Python Chroma 不会自动看到新内容，客服仍会根据旧规则回答。 |
| 实际流程 | 管理员必须提供 `.md/.txt`、规则类别和 HTTPS 公开来源；Node 存储原文、分块和 SHA-256 指纹后，仅将公开正文/来源元数据发送给 localhost FastAPI；Python 用 BGE 编码并以 `documentId + fingerprint + chunkIndex` 进行 Chroma upsert。 |
| 状态与审计 | 文档和向量状态分离：`processingStatus` 说明原文是否已分块，`vectorIndexStatus` 记录 `pending → syncing → synced/failed`。成功写入索引版本和时间；失败保留错误摘要并追加审计，管理员可重试。 |
| 安全边界 | 普通用户被 `adminProcedure` 拒绝；Python 不接收 Cookie、用户 ID、订单/工单、数据库凭据或 LLM 密钥；非 HTTPS 来源在 Node 和 Python 两层拒绝。 |
| 当前限制 | Chroma 仍是容器本地派生索引。当前新增文档能在同一 sidecar 中即时生效；新的 Python 运行实例会在首次公开规则请求前，由 Node bootstrap 当前 `active + ready + synced` 文档。该恢复不是跨容器持久化，且当前不使用常驻队列。 |
| API 级验证 | 集成测试通过真实 `adminRouter.uploadKnowledgeDocument` 先验证 Python 不可用时的 `failed` 状态，再调用真实 `retryKnowledgeVectorSync` 获得 `synced` 版本，并由 Node 客服返回新规则引用；测试末尾清理临时文档。 |

> **面试追问：为什么要把“文档已上传”和“向量已同步”分开？**  
> 前者表示事实记录安全落在对象存储/MySQL，后者才表示派生索引可被客服检索。分开状态可以避免索引失败时前端显示“规则已生效”，也让重试、审计和后续重建有明确的责任边界。

## 12. 已实现：规则生命周期与轻量索引运维

| 维度 | 实际结果、问题与应对 |
|---|---|
| 业务目的 | 增量同步只能解决“新规则进入当前 Chroma”的问题，不能回答“旧规则何时停止被引用”“sidecar 重启后如何恢复”或“管理员如何一次性检查并修复全部有效规则”。因此将规则版本、生命周期与派生索引恢复纳入同一条管理链路。 |
| 生命周期与替换顺序 | `knowledgeDocuments` 保存 `active`、`superseded`、`retired` 生命周期、版本号、替代关系和失效原因。替换时先创建并同步新版本；只有新版本 `synced` 后才将旧版本标记为 `superseded` 并从 Chroma 删除，避免新版本失败时提前丢失仍可用的旧规则。 |
| 运行时 bootstrap | Python `/health` 返回 `runtimeInstanceId`。Node 在首次公开规则请求前识别新的运行实例，查询 MySQL 中 `active + ready + synced` 的管理员规则，并逐份调用 localhost upsert；bootstrap 只恢复当前 Chroma 派生索引，不会改写事实记录或生命周期。 |
| 失效与批量重建 | 管理员失效规则时，Node 先保留原文与操作原因，再请求 Python 按 `documentId` 删除 Chroma 分块，并写入 `knowledge.retire` 审计；管理员批量重建在同一请求内逐份同步，返回 `total/succeeded/failed`，不引入常驻异步队列。 |
| 预期问题 | BGE sidecar 首启会比公开客服短超时更慢；若重建路径沿用短窗口，管理员会看到同步失败，且旧规则可能在版本切换中产生不一致风险。 |
| 当前应对与局限 | 管理员文档写入使用受控的冷启动重试窗口，公开客服仍可在短超时后降级到 Node TF-IDF；Python 永不接收订单、用户、Cookie 或密钥。请求内模式适合当前单文件不超过 100KB 的小规模演示语料；当文档数量或耗时上升时，应以容量数据为依据迁移到持久队列。 |
| 验证证据 | 规则生命周期集成测试覆盖“上传 v1 → 成功同步 v2 → v1 为 superseded → 新运行实例 bootstrap → 客服只引用 v2 → 失效 v2 后不再引用”；完整回归为 42 项 TypeScript 与 7 项 Python Agent 测试。 |

> **面试追问：为什么不能先把旧规则下线，再尝试同步新规则？**  
> 这样会在新规则向量化、网络或模型加载失败时制造知识空窗。CampusMate 采用“新版本先成功同步、旧版本后 supersede”的顺序：事实源保留两份历史，Chroma 仅删除已确认被替代的旧版本分块。

> **面试追问：为什么当前不使用消息队列？**  
> 管理员规则变更频率低、单文件限制为 100KB，作品集场景更需要操作结果立即可见和失败可复现，因此采用请求内同步。代价是批量重建不能无限扩展；未来应先采集文档数、耗时和失败率，再引入持久队列、幂等任务和状态看板，而不是为了堆技术名词提前复杂化。

> **面试追问：为什么资料编辑不允许用户修改邮箱和角色？**

> **面试追问：为什么“禁止最后管理员被降级”还不够？**  
> 这只是最小安全条件。生产系统还需要双人审批、短期高风险操作令牌、角色变更通知、分页/筛选和更丰富的权限模型。当前项目通过显式策略函数与单元测试展示核心不变量，但不把它表述为企业级 IAM。

## 15. 已修复：预览参数下的 tRPC HTML 响应错误

| 维度 | 实际结果、问题与应对 |
|---|---|
| 现象 | 管理台在 `/admin?from_webdev=1` 环境中出现 `Unexpected token '<'`。这类报错表示 tRPC 客户端预期 JSON，却收到了以 `<!doctype html>` 开头的 SPA 页面。 |
| 根因判断 | 已验证正常 tRPC 路由注册在 Vite/静态回退之前，且当前带预览参数的管理台可稳定加载。风险点在于通用 `*` SPA 回退此前会为任何未命中的路径返回 `index.html`；若 API 路由在开发重启、代理或路径拼接异常时未命中，客户端只能看到 HTML 解析错误而非可诊断 API 错误。 |
| 修复 | tRPC link 显式固定到 `window.location.origin` 下的 `/api/trpc`，不继承页面查询参数。Vite 开发回退与生产静态回退共同识别 `/api` 路径，未命中时返回 JSON 404，不再返回 HTML。 |
| 验证证据 | `apiFallback.test.ts` 验证 `/api/trpc/...?...&from_webdev=1` 被识别为 API，而 `/admin?from_webdev=1` 仍进入 SPA；实际 curl 验证匹配的 tRPC 端点返回 `application/json`，未命中 `/api/unknown` 也返回 JSON 404；截图验证管理台在预览参数下加载用户目录。 |

> **面试追问：为什么不只在前端捕获 JSON 解析错误？**  
> 捕获只能改善提示，不能修复协议边界。HTTP API 应保证 API 路径返回 JSON；把未匹配的 API 请求错误地回退成 HTML 会掩盖真实路由问题，也让客户端无法区分权限错误、404 和页面回退。CampusMate 在服务端回退处保证响应类型，并在客户端固定 API 基址。

| 前端交付边界 | 记录 `/`、商品、订单、客服、个人中心、登录、后台、评测和项目说明等实际路由；不把动态页或后台模块凑成 15 页。未采集 Lighthouse/Web Vitals，继续禁止“两秒加载”主张。 |

> **面试追问：为什么 Recall@3 100% 仍不能说检索已经足够好？**  
> 这个结果来自 3 份短文档和 6 个已知答案问题，且衡量的是 Node 回退检索的文档级命中，不是开放世界的用户语言、Chroma/BGE 在线召回或回答正确性。它的价值是给出可复现基线；下一步应扩充独立公开规则集、人工标注相关片段并分模型报告。

> **面试追问：为什么要区分 `max_tokens` 和 `max_completion_tokens`？**  
> GPT-5 类模型会消耗推理 token；若只给很小的统一上限，可能在产生函数参数前结束。兼容参数让工具调用获得足够的完成预算，但不会改变 Node 对模型输出的 JSON、会话和权限二次验证。

## 18. 已实现：普通用户发布与个人工单进度

| 维度 | 实际结果、问题与应对 |
|---|---|
| 业务目标 | 补全“浏览—发布—审核—展示”的卖方链路，并让用户在个人中心无需进入管理员后台即可了解自己发起的模拟人工工单处于已提交、处理中还是已解决。 |
| 发布流程 | `/publish` 只在登录后调用受保护的 `catalog.publish`。用户提交分类、标题、价格、成色、10–2000 字详细描述与 1–3 张图片；服务端校验字段、JPEG/PNG/WebP MIME 和 2MB 单图上限，再由 Node 写入对象存储，并将 `storageKey/url` 保存到 `productImages`。 |
| 状态与隔离 | 新商品固定为 `pending_review`，公开商品列表与公开详情只读取 `active`，因此未审核内容不会被直接 URL 暴露。管理员通过 `adminProcedure` 审核上架；商品归属由服务端从会话写入 `sellerUserId`，发布与审核均追加审计。 |
| 工单进度 | `profile.mine` 同时聚合当前 `userId` 的订单、发布物品和模拟工单；页面将 `open / in_review / resolved` 映射为已提交、处理中、已解决的进度条，不增加对其他用户工单的查询路径。 |
| 预期问题 | 图片 data URL 会导致请求体膨胀；若只靠前端限制格式或状态，攻击者能绕过 UI 直接调用接口；若将待审核商品混入公共 `get`，用户可猜测 ID 查看未审核内容。 |
| 当前应对与局限 | 双端校验图片格式/大小，服务端只存对象键与 URL；公开读取强制 `active` 条件，管理员读取/审核另走受限过程。作品集版本未接入病毒扫描、OCR 内容审核、支付、物流或真实客服；大图、多图和高并发场景应改用预签名直传、异步审核和对象存储生命周期策略。 |
| 验证证据 | `userListingPolicy.test.ts` 覆盖图片格式和体积拒绝；`userPublish.auth.test.ts` 覆盖匿名发布拒绝；`userPublish.integration.test.ts` 覆盖存储引用、当前卖家归属、`pending_review` 与公开目录隔离；个人中心集成测试断言发布物品和工单均归当前用户。桌面截图验证发布表单、待审核提示与工单进度区。 |

> **面试追问：为什么上传图片后不立即公开商品？**  
> 图片和描述都来自用户输入，即使是作品集演示也不应默认可信。CampusMate 先将数据与归属安全保存，再用 `pending_review` 将公开读路径隔离；管理员审核后才变为 `active`。这是发布状态机与公共内容边界，而不是前端“隐藏卡片”。

> **面试追问：为什么个人中心不直接读取管理员工单队列？**  
> 管理员队列包含其他用户的摘要、身份信息和操作入口。个人中心只通过 `userId` 查询本人 `supportTickets`，并复用服务端审计；即使客户端手工传入别人的 ID，也没有对应的 tRPC 输入可以改变查询所有者。

## 19. 已实现：发布物品管理与管理员批量审核

| 维度 | 实际结果、问题与应对 |
|---|---|
| 业务目标 | 补齐发布后的自助管理闭环：发布者可改正信息、主动撤回或针对拒绝原因修订后重提；管理员可从审核队列按状态筛选并一次处理多件待审核商品。 |
| 状态模型 | `products.status` 新增 `rejected`，并增加可空 `reviewReason`。允许编辑的 `pending_review / active / archived / rejected` 会统一回写到 `pending_review`；撤回转为 `archived`；仅 `rejected / archived` 可重提；`reserved` 商品不允许编辑或撤回。 |
| 所有权与编辑 | `/profile/listings` 仅请求当前 `profile.mine` 的 `sellerUserId` 记录；`updateUserListing`、`withdrawUserListing`、`resubmitUserListing` 都用 `productId + sellerUserId` 查询、事务行锁和纯状态机策略二次校验，并对允许与拒绝操作追加审计。编辑可保留已有对象存储图片，或整组替换为经服务端再次校验的新图片。 |
| 批量审核 | 管理员列表按状态调用受限 `admin.products`。`batchReviewProducts` 对每个唯一商品 ID 逐项锁定、复核仅 `pending_review` 可审核，再写 `active/rejected`、拒绝原因与审计；返回通过、拒绝和跳过计数，不对已被处理、预留或不存在的商品做静默覆盖。 |
| 预期问题 | 如果只在前端隐藏“编辑”按钮，篡改 ID 仍可能越权；如果编辑后保留 `active`，新内容会绕过旧审核结论；如果批量审核用无条件 `UPDATE id IN (...)`，页面停留期间发生的并发状态变化会被误改。 |
| 当前应对与局限 | 用户身份永远从 `ctx.user.id` 获取，编辑统一重回审核并清空旧 `reviewReason`；批量操作采用逐项状态策略与跳过结果。当前演示没有病毒扫描、图片内容审核、预签名直传或多管理员冲突通知，生产化时应将大文件直传与异步审核拆开。 |
| 验证证据 | `listingLifecycle.test.ts` 覆盖合法/非法转换；`listingManagement.integration.test.ts` 覆盖本人编辑—撤回—重提和非所有者拒绝；`adminBatchReview.auth.test.ts` 覆盖普通用户在管理员过程之前被拒绝；OAuth 回跳测试增加 `/profile/listings` 白名单验证。桌面验证显示发布管理页的编辑/撤回/重新提交入口，以及管理台审核队列的状态筛选、复选框、批量通过和拒绝原因输入区均可见。 |

> **面试追问：为什么编辑后要重新审核，而不是保留已上架状态？**  
> 标题、描述、价格和图片都是可变的用户输入。若编辑后继续 `active`，新的内容会绕过管理员针对旧版本作出的审核结论。因此系统把允许编辑的状态统一回写为 `pending_review`，清除旧拒绝原因，并让管理员判断新版本。

> **面试追问：为什么批量审核允许“部分跳过”而不是整批失败？**  
> 选择商品到提交之间存在时间窗口，某一件可能已被其他管理员处理、撤回或不再满足待审核条件。逐项行锁和状态机允许仍合法的项目完成，同时把不合法项目显式标记为跳过并写审计，比“全部成功”的模糊结果更可追溯。

## 21. 管理员系统状态与审核历史

| 维度 | 实现与原因 | 风险与处理 |
|---|---|---|
| 系统状态 | 管理员 `systemStatus` 过程并行读取 FastAPI `/health` 与规则文档/分块统计，展示 Agent 可用性、运行实例、Embedding、索引版本、向量同步状态和最后索引时间。 | 健康检查会因 sidecar 冷启动、模型加载或服务不可用失败；页面明确标记“需要关注”，不把上一轮状态伪装成当前成功。 |
