# CampusMate 工程流程与面试深挖日志

**使用规则：** 本文不是项目宣传稿，而是用于你真正理解业务和应对面试追问的工程日志。每次新增、修改或修复功能时，都要新增一条记录：说明业务为什么需要它、数据如何流动、最可能出什么问题、实际如何验证、以及面试官可以如何追问。

## 0. 用一句话讲完整业务流程

用户先在公开商城发现演示商品；登录后才能创建模拟订单。订单进入以 OAuth 会话隔离的个人空间，用户可以在订单页、个人中心或 AI 客服中查询自己的记录。客服对规则问题先检索公开来源改写的知识库，对商品与订单问题调用受控服务端工具；当证据不足或用户主动转人工时，系统不伪造答案，而是允许登录用户保存只属于自己的模拟工单。管理员负责商品、知识库与固定评测，评测记录用于验证关键链路而不是制造漂亮分数。

```text
公开商品浏览
  → OAuth 登录
  → 模拟下单（订单快照 + 商品预留 + 审计）
  → 本人订单 / 个人中心
  → AI 客服：意图 → 检索或受控工具 → 引用回答 / 拒答转人工
  → 模拟工单（仅当前会话可见）
  → 管理员知识库与固定评测
```

## 1. 商城发现与模拟下单

| 维度 | 记录 |
|---|---|
| 业务问题 | 校园二手用户需要先通过商品、分类、关键词和详情判断物品是否值得进一步联系，而不应被登录门槛阻断公开浏览。 |
| 用户路径 | 首页/全部商品 → 搜索或筛选 → 商品详情 → 登录 → 创建模拟订单 → 我的订单。 |
| 数据流 | `products`、`categories`、`productImages` 提供公开目录；下单创建 `orders` 与 `orderItems` 快照，并将商品状态改为 `reserved`。 |
| 安全边界 | 创建订单由服务端会话的 `ctx.user.id` 决定，不接收客户端指定买家 ID；非 `active` 商品拒绝下单。 |
| 常见问题 | 两个用户同时对同一商品下单可能产生竞争；演示版依赖状态判断，生产环境应使用事务内带条件更新或乐观锁保证只预留一次。 |
| 当前应对 | 下单写入订单、订单项和商品预留状态处于同一数据库事务；商品不再为 `active` 时会拒绝后续请求。 |

> **面试追问：为什么订单要保存商品标题和价格快照？**  
> 因为商品本身后续可能下架、改名或价格调整；订单必须保留创建时的交易语义，不能每次展示时重新读取当前商品字段。

## 2. OAuth、订单所有权与追加式审计

| 维度 | 记录 |
|---|---|
| 业务问题 | 二手交易最敏感的数据是订单。前端隐藏“别人的订单”无法阻止直接请求 API，因此必须在服务端验证所有权。 |
| 用户路径 | 登录后查看订单列表 → 点击详情 → AI 查询“我的订单”。 |
| 数据流 | Manus OAuth 生成会话；tRPC 上下文提供当前用户；订单读取以 `orders.userId` 与当前用户 ID 比较；审计写入 `auditLogs`。 |
| 安全边界 | `protectedProcedure` 阻止匿名读取；`getOrderForActor` 通过所有权决策拒绝跨账户请求；允许和拒绝路径均有审计事件。 |
| 常见问题 | 受管 TiDB 不支持触发器，无法用数据库 trigger 强制审计；若只靠前端限制，越权请求仍可能读取数据。 |
| 当前应对 | 审计日志只暴露应用层追加写入路径，禁止更新/删除；核心订单读取流程统一经过审计封装，并由测试覆盖允许和拒绝分支。 |

> **面试追问：为什么不让客户端传一个 `userId`，服务端再比对？**  
> 客户端参数本身是不可信输入。最安全的做法是从已验证的会话中取身份，再把它作为查询条件；这样攻击者即使篡改请求体，也无法指定另一位用户。

## 3. 知识库处理与可引用 RAG

| 维度 | 记录 |
|---|---|
| 业务问题 | 交易规则、售后说明和安全 FAQ 分散在文档中。客服若仅靠模型记忆回答，既不能解释来源，也容易把演示规则说成正式平台政策。 |
| 用户路径 | 管理员初始化或上传 Markdown/TXT → 文档处理为知识块 → 用户问规则问题 → 页面展示回答和公开来源。 |
| 数据流 | `knowledgeDocuments` 保存元数据和来源；`knowledgeChunks` 保存内容、来源标签与词项向量 JSON；检索结果带文档 ID、分数和 URL。 |
| 当前算法 | 文本按段落聚合为确定性分块；使用语料级 TF-IDF 和余弦相似度召回 Top-3。检索有分数但不等于语义 Embedding。 |
| 常见问题 | 关键词重叠可能造成伪相关；文档太短、来源不可访问或分块过大都会降低检索质量。 |
| 当前应对 | 罕见词 IDF 测试、无关问题拒答测试、来源 URL 展示与低置信转人工；文档上传限制格式与长度。 |

> **面试追问：为什么不用模型直接回答？**  
> 模型负责压缩和表达，不负责决定事实。检索阈值和引用返回由程序控制，低置信时必须拒答；这样才能解释“依据是什么”和“为什么不回答”。

> **面试追问：TF-IDF 的局限是什么？**  
> 它依赖词面匹配，近义表达与复杂语义理解较弱；当前选择它是为了零外部向量服务、可复现和便于演示。后续可保持文档、引用和阈值接口不变，替换为 Embedding + 向量库。

## 4. AI 客服 Agent 与受控工具

| 维度 | 记录 |
|---|---|
| 业务问题 | “客服”不能只回答规则，还需要在安全前提下找商品、查询本人订单并将无法处理的问题转人工。 |
| 工作流 | 接收问题 → 规则意图分类 → 选择知识检索/商品检索/本人订单/人工转接 → 返回回答、引用、工作流轨迹和工具结果。 |
| 当前工具 | `knowledge_search`、`product_search`、`own_order_lookup`、`handoff_advice`。工具均由 TypeScript 服务端显式调用。 |
| 当前实现边界 | 这是显式状态工作流，不是 LangGraph；也是受控业务工具调用，不是大模型原生 Function Calling。 |
| 常见问题 | 如果将订单工具直接暴露给模型，模型或提示注入可能诱导工具传入其他订单 ID；如果错误处理不当，LLM 不可用会导致客服完全不可用。 |
| 当前应对 | 订单工具只接收会话身份，所有权校验在业务层；规则回答有检索证据 fallback，即使模型暂不可用也会返回基于证据的安全摘要。 |

> **面试追问：Agent 的状态在哪里？**  
> 当前每次请求构造一个显式状态对象，以“接收、意图、工具、回答、转人工”步骤数组返回前端并可保存到工单。这使单轮决策可解释；若要支持长期多轮记忆或恢复，需要新增会话表和持久化状态机。

> **面试追问：为什么 `ask` 可以匿名调用，而订单工具不能？**  
> 公开规则和商品目录没有个人敏感性，所以允许匿名体验；一旦路由到订单工具，缺少会话会被阻止，并返回登录说明，不会执行订单查询。

## 5. 模拟人工工单

| 维度 | 记录 |
|---|---|
| 业务问题 | “转人工”若只是一句文案，无法展示交接信息如何沉淀，也不能体现工单的权限模型。 |
| 用户路径 | 无匹配规则或主动请求人工 → 客服生成转人工工作流 → 登录用户点击创建模拟工单 → 我的模拟工单显示记录。 |
| 数据流 | `supportTickets` 保存当前用户 ID、分类、原问题、回答摘要、工作流轨迹、状态和演示标识；创建/查询追加审计日志。 |
| 安全边界 | 创建和查询使用 `protectedProcedure`；列表查询固定 `where userId = ctx.user.id`，客户端没有指定目标用户的入口。 |
| 常见问题 | 若工单摘要包含模型自由生成内容，可能出现误导；若管理员工单处理没有角色校验，会造成泄露。 |
| 当前应对 | 当前仅保存客服已返回的演示摘要，明确标记不联系真实客服；管理员处理队列尚未实现，不能声称有真实客服系统。 |

> **面试追问：为什么把工作流轨迹也保存到工单？**  
> 转接人员需要知道用户问了什么、系统尝试了哪些工具、为什么没有直接回答。保存轨迹可以减少重复问询，也便于审计模型/检索失败分支。

## 6. 个人中心、管理员后台与固定评测

| 模块 | 业务价值 | 常见问题与应对 |
|---|---|---|
| 个人中心 | 将订单轨迹和已发布物品放入同一用户空间，让演示从“浏览”走到“个人业务状态”。 | `sellerUserId` 是后加字段，历史演示目录缺少归属；当前以管理员账户为演示目录归属并只按字段查询，普通用户保持空态隔离。 |
| 管理后台 | 管理员可维护商品、初始化知识库与上传规则文档。 | 前端不展示入口不足以安全；服务端 `adminProcedure` 对直接请求也返回 `FORBIDDEN`。 |
| 固定评测 | 将规则、无匹配、商品、本人订单、跨账户订单、人工转接 6 类案例写入数据库并记录实际运行。 | 评测指标不等于生产 SLA；当前延迟为本次服务端运行时间，应明确注明采样边界。 |

> **面试追问：为什么要用固定案例，而不是只演示几句提问？**  
> 临时演示不可复现，容易挑选对系统有利的问题。固定案例使预期意图、引用、拒答与延迟都有可追溯基线，变更后可以发现回归。

## 7. 已发生问题与工程处理记录

| 事件 | 原因判断 | 处理方式 | 可迁移经验 |
|---|---|---|---|
| 个人中心的演示商品没有归属 | 早期商品表没有 `sellerUserId`，种子数据也早于该字段。 | 增加迁移、索引和按当前用户查询；对无归属演示商品安全地归属到演示管理员。 | 数据模型演进必须考虑历史数据的兼容策略。 |
| 工单模拟功能缺少数据闭环 | 早期“转人工”只返回文本，不可追踪也无法展示隔离。 | 新建 `supportTickets`、受保护 API、审计和集成测试。 | 每个业务“下一步”都应有数据实体与权限规则，而不只是 UI 文案。 |
| 固定评测扩展后测试失败 | 新增人工转接案例后，旧测试仍断言 5 个案例。 | 同步更新案例计数断言并重跑全套测试。 | 改变评测数据集本身就是行为变更，测试的期望集也必须版本化。 |
| 生成构建出现大包警告 | Mermaid/高亮相关依赖使部分 bundle 超过警告阈值。 | 当前构建成功，记录警告但不伪称性能已优化。 | 性能主张必须区分构建通过、HTTP 响应与真实浏览器体验。 |
