# CampusMate 项目基础要求与长期执行约束

**定位：** 本文是 CampusMate 的长期基线。每次新增功能、调整技术方案或准备简历/录屏材料前，必须先回顾本文；每次保存检查点前，必须确认本文和 `docs/engineering-and-interview-log.md` 已同步更新。

## 1. 项目核心目标

CampusMate 不是一个只展示页面效果的商城 Demo，而是一套用于作品集和面试深挖的 **AI 应用工程案例**。它要让使用者能够完整讲清楚校园二手交易从商品发现、模拟下单、订单隔离、规则咨询、受控工具调用、人工转接到评测与审计的业务闭环。

| 目标维度 | 必须达到的效果 | 面试中应能讲清楚的重点 |
|---|---|---|
| 用户体验 | 学院编辑风的校园二手商城；桌面与移动端都能发现商品、订单、AI 客服、个人中心（含本人资料、发布审核、发布物品管理和工单进度），以及清晰区分的普通用户注册/登录与管理员授权入口。 | 为什么商城前台用公开浏览，涉及发布、订单与工单时才进入登录边界；为什么管理员入口不等于自助提权。 |
| 业务闭环 | 商品浏览 → 普通用户发布待审核闲置物品 → 本人编辑/撤回/重新提交 → 管理员筛选并批量审核 → 公开展示或拒绝反馈 / 模拟下单 → 我的订单、发布审核和工单进度 → AI 查询本人订单 → 转人工模拟工单。 | 每一步产生了什么数据、由谁读取、如何回到下一步。 |
| RAG 可信性 | 规则回答先检索可引用证据；无足够证据时拒答并引导人工支持。 | 为什么不能让模型自由生成规则；证据和回答分别由什么模块控制。 |
| 权限安全 | 订单、发布物品、工单和可编辑资料均按当前 OAuth 会话的用户 ID 查询；管理员角色变更使用服务端门槛与追加式审计。 | 为什么前端隐藏菜单不等于安全；服务端如何处理直接 API 请求和管理员误操作。 |
| 工程可验证性 | 重要边界拥有自动化测试，固定评测保存实际运行记录，页面有桌面/移动端验证。 | 测试覆盖什么、不覆盖什么，如何复现评测和失败分支。 |

## 2. 当前真实技术边界

当前项目是 **React 19 + TypeScript + Tailwind CSS + Express 4 + tRPC 11 + Drizzle ORM + MySQL/TiDB + Python FastAPI + LangGraph + Chroma + FastEmbed ONNX** 双运行时应用。Python 服务只处理公开问题的意图路由与 Chroma 演示规则召回，使用 `BAAI/bge-small-zh-v1.5` 预训练中文语义 Embedding；Node 网关保留 OAuth、LLM 密钥、订单与工单工具，并保留语料级 TF-IDF/余弦检索作为安全回退。检索、引用、阈值判断、订单所有权与工单权限均由服务端程序控制。

用户身份使用 Manus OAuth，不在 CampusMate 数据库中保存密码。普通用户首次授权会通过 OAuth 回调创建默认 `user` 角色档案；管理员入口只携带白名单站内回跳目标 `/admin`，不能改变角色。回调仍先验证一次性 nonce，再仅允许 `/`、`/profile`、`/profile/listings` 或 `/admin` 四个站内目标；管理员权限始终由服务端 `role` 与 `adminProcedure` 决定。

个人中心的 `profileName`、`campus`、`major`、`bio` 是独立于 OAuth 姓名/邮箱的可编辑资料，更新接口只从会话取得 `userId`，不接收客户端指定的目标用户。管理员可查看用户目录并修改**其他**账户的 `role`；服务端会阻止修改自身角色、降级最后一名管理员，并对允许与拒绝的角色操作追加审计记录。

前端 tRPC 客户端固定使用当前浏览器 origin 下的绝对 `/api/trpc` 端点，不继承页面查询参数。开发和生产的 SPA 回退会将任何未命中的 `/api` 请求返回 JSON 404，而不是 `index.html`；因此即使管理台带 `from_webdev=1` 预览参数，API 客户端也不会把 HTML 当作 JSON 解析。

客服 Agent 的 OpenAI-compatible 原生 Function Calling 仅用于选择 `search_catalog`、`own_order_lookup` 与 `create_support_ticket` 三个受限工具。模型从不接触 Cookie、用户 ID、订单、数据库或密钥；Node 会重新验证参数、登录状态与显式人工请求，再执行本地商品、订单或模拟工单操作。工单处理状态只允许管理员通过 `adminProcedure` 从 `open` 推进到 `in_review` 或 `resolved`，并追加审计记录。

> **真实性红线：** 当前版本可以描述为 Python、FastAPI、LangGraph、Chroma 和预训练中文语义 Embedding 项目；管理员上传的 HTTPS 公开规则会在当前 sidecar 运行时增量同步至 Chroma，并有状态、失败摘要、管理员重试、版本替换与失效审计。每个新的 Python 运行实例会在首次公开规则请求前 bootstrap 当前 `active + ready + synced` 文档；必须同时说明 Chroma 是容器本地派生索引，MySQL/对象存储才是事实源。PHP、“15 个核心页面”与“页面加载 2 秒内”仍不得写入简历，因为没有相应实现或测量报告。

| 能力 | 当前真实实现 | 不应混淆的替代表述 |
|---|---|---|
| 文档处理 | Markdown/TXT 上传；对象存储和 MySQL 保留事实记录；管理员 HTTPS 公开规则由 Node 增量写入 Python Chroma，Python 使用带重叠的滑动窗口；规则具备 `active/superseded/retired` 生命周期、请求内 bootstrap 与同步批量重建。 | Chroma 为容器本地派生索引；bootstrap 由首次公开规则请求触发，当前不使用常驻异步队列，适用于受控的小规模演示语料。 |
| 检索 | Python Chroma 通过 FastEmbed ONNX 运行 `BAAI/bge-small-zh-v1.5` 的 512 维预训练中文语义向量 Top-K；Node TF-IDF/余弦仅作回退，均返回分数和来源；另有公开规则 6 题固定集计算 Node 回退的 Recall@3/MRR。 | 固定 5 题 BGE/哈希比较和 6 题 TF-IDF/余弦评测都只描述当前演示语料，不能外推为生产准确率。 |
| Agent | LangGraph 状态图：接收 → 意图 → Chroma 检索/交还 Node 网关；OpenAI-compatible 原生 Function Calling 选择受限工具，Node 负责授权与执行。 | Function Calling 是编排信号，不授予模型数据库、订单或密钥访问权。 |
| 工具 | 商品检索、本人订单查询、模拟工单创建/查询和管理员工单状态流转。 | 商品、订单与工单工具均由 Node 重新验证参数、会话与显式人工请求后执行。 |
| 用户发布与审核 | 普通用户通过受保护 tRPC 过程提交分类、标题、价格、成色、描述及 1–3 张 JPEG/PNG/WebP 图片；Node 校验后写对象存储引用、商品/图片元数据和审计，初始状态为 `pending_review`。本人只能管理 `sellerUserId` 匹配的记录：编辑会回到 `pending_review`，撤回变为 `archived`，`rejected/archived` 可重新提交；`reserved` 禁止编辑或撤回。管理员按状态筛选，仅对 `pending_review` 商品逐项事务锁定后批量通过为 `active` 或拒绝为 `rejected`，拒绝原因写入商品和审计。 | 不含支付、真实交易、内容审核模型或恶意文件扫描；待审核和拒绝物品不能被公开目录或公开详情读取。批量审核会逐项返回跳过结果，不能把过期、预留或不存在商品误改为已上架。 |
| 性能 | 已记录开发服务本地 HTTP 响应基线。 | 不等同于真实浏览器页面加载或生产 SLA。 |

完整逐项审计见 [`docs/ai-agent-capability-audit.md`](./ai-agent-capability-audit.md)，简历可用版本见 [`docs/resume-ready-campusmate.md`](./resume-ready-campusmate.md)。

## 3. 业务流程验收基线

| 阶段 | 用户可见动作 | 服务端处理与数据变化 | 安全/失败边界 |
|---|---|---|---|
| 商品发现 | 浏览、搜索、筛选和查看商品详情。 | 查询公开演示目录与商品图片。 | 不展示真实交易或支付能力。 |
| 模拟下单 | 登录后在商品详情创建订单。 | 创建订单与订单快照，将商品设为预留，追加审计。 | 未登录不能创建；非 active 商品不能下单。 |
| 发布闲置与管理 | 登录用户在 `/publish` 填写分类、标题、价格、成色、详细描述并上传 1–3 张图片；随后可在 `/profile/listings` 编辑、撤回或重新提交自己的物品。 | 服务端验证 MIME/大小/字段，写入对象存储引用与 `productImages`，以会话用户写入 `sellerUserId` 和 `pending_review` 商品，并追加审计；编辑清除旧拒绝原因并重回审核，撤回变为 `archived`，拒绝/撤回可重提。 | 不接受 GIF/SVG/超 2MB 图片；`reserved` 商品禁止编辑/撤回；新商品不进入 `active` 公共目录或公开详情，且用户不能传入或替换他人的 `sellerUserId`。 |
| 订单与个人中心 | 查看本人订单轨迹、发布物品、发布审核、模拟工单进度与基本资料；可编辑昵称、学校、专业、简介。 | 以会话用户 ID 分别过滤订单、`sellerUserId` 与工单 `userId`，并以同一 ID 更新独立 profile 字段。 | OAuth 姓名、邮箱和角色不可在个人中心修改；其他用户资料、发布记录或工单不进入查询或更新路径。 |
| 规则咨询 | 在客服页询问上架、售后或安全规则。 | 检索知识块、判断证据阈值、以证据生成回答并返回引用。 | 无匹配时禁止猜测，转人工建议。 |
| 商品/订单工具 | 询问商品或“我的订单”。 | 原生 Function Calling 可选择商品/本人订单工具，Node 重新校验后执行并返回结构化工作流与工具结果。 | 未登录订单查询被阻止；越权订单读取拒绝并审计。 |
| 人工转接 | 对无匹配或主动转人工请求创建模拟工单。 | 仅在登录且明确请求人工、转接、投诉或工单时允许工具创建；保存问题、摘要、工作流和当前用户 ID，管理员可推进处理状态。 | 用户只看本人历史工单；不联系真实客服；模型不能自行跳过同意门槛。 |
| 管理与评测 | 管理员按状态筛选商品，批量通过或拒绝待审核物品，维护知识库、用户角色、模拟工单队列并运行固定 Agent/检索评测。 | `adminProcedure` 校验，批量审核在事务中逐项锁定并对每项写审计；角色和工单状态变更同样追加审计；评测展示固定 6 类 Agent 案例与 6 题检索质量。 | 普通用户 API 调用仍被服务端拒绝；非待审核/不存在商品会作为单项跳过而非被误改；管理员不能修改自身角色或移除最后管理员；检索指标不是生产 SLA。 |

## 4. 非功能验收要求

每个新增功能必须至少满足下表中的相关项，不能只实现“看起来能点”的前端界面。

| 检查维度 | 最低要求 |
|---|---|
| 数据模型 | 明确表、字段、所有者、状态和数据生命周期；迁移经审阅后才应用。 |
| 服务端 | tRPC 过程明确区分公开、登录和管理员边界；不信任客户端传入的身份或角色。 |
| 前端 | 有加载、空态、错误态和移动端布局；不把未实现操作伪装为真实功能。 |
| 测试 | 至少补充正常路径、拒绝/失败路径和关键所有权边界测试。 |
| 评测 | 若功能影响 Agent，补充固定案例或说明为何不应纳入评测。 |
| 文档 | 更新本基线、工程/面试复盘日志、README 和录屏脚本中的相关段落。 |
| 性能 | 只记录实际采样指标，并写清采样环境、方法与不适用边界。 |

## 5. 产品界面与工程资料的分层

CampusMate 的网页界面面向使用者和管理员交付，因此只保留业务、数据披露、服务说明、权限保护与质量监控内容，不展示“面试”“简历”“作品集”“答辩”或“复盘”等求职导向文字。面向维护者的工程细节、技术取舍、失败分支、代码摘录与自动化验证集中写入仓库文档，不作为普通产品界面的功能入口。

| 资料层级 | 面向对象 | 当前入口/文件 | 内容边界 |
|---|---|---|---|
| 产品界面 | 校园用户与管理员。 | `/`、`/goods`、`/profile`、`/admin`、`/project`、`/evaluation`。 | “服务说明”和“质量监控”使用产品化语言解释数据、权限和服务状态。 |
| 需求与架构 | 交付方、维护者和技术沟通对象。 | `docs/requirements-and-architecture.md`。 | 需求编号、验收条件、架构选择和非功能约束。 |
| 正式需求与录屏 | 交付方、维护者和产品评审者。 | `docs/product-requirements-document.md`、`docs/demo-recording-script.md`。 | 按角色、流程和验收条件说明产品；录屏分镜只引用当前真实页面与数据披露。 |
| 技术交付说明 | 开发与维护人员。 | `docs/technical-delivery-guide.md`。 | 技术栈、数据模型、业务流程、代码摘录、安全边界、测试和运行命令。 |
| 工程日志 | 项目负责人。 | `docs/engineering-and-interview-log.md`。 | 历史问题、判断过程、深度技术问答与迭代记录，不作为产品界面文案。 |

管理员可观测能力也遵循最小披露：系统状态只呈现 Agent 健康、模型/索引版本和规则文档统计，不呈现密钥、Cookie、订单或账户私密字段；单件审核详情只呈现审核所需的商品、图片、发布者必要上下文和该商品的追加式审计历史。

GitHub 交付采用私有仓库作为默认可见性。源码仓库不提交环境变量、构建输出、日志、Python 运行时派生索引、真实凭据或原始录屏素材；演示视频如需公开，应先确认画面不含邮箱、Cookie、终端凭据或其他可识别的个人信息。

## 6. 每轮开发的强制复盘流程

1. **开始前：** 在 `todo.md` 写入可验证任务，并在工程日志中先记录目标业务流程、预期数据变化与可能失败点。
2. **实现中：** 遇到数据库、认证、检索、模型、构建或 UI 问题时，记录根因、判断过程、采取的应对和仍存局限。
3. **完成后：** 运行对应测试、类型检查、必要时生产构建与桌面/移动端截图；将结果写入工程日志。
4. **保存前：** 复读 `todo.md`，同步更新本文、工程/面试日志、README 与录屏脚本；任何尚未验证的能力不得写成已完成。

> 后续每次用户要求新增、修复或重构功能时，本文件和工程/面试日志都是交付物的一部分，而不是一次性说明材料。
