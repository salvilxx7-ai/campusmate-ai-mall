# 参考商城构建流程与迁移边界

## 参考来源与许可

CampusMate 参考了开源项目 [Kraizan/Second-Hand](https://github.com/Kraizan/Second-Hand) 的校园二手交易业务场景与页面流。参考仓库使用 **MIT License**，固定参考提交为 `dc795b3`。CampusMate 将保留许可证与来源说明；本项目不会直接复制原项目的应用代码，而是基于其业务概念，在 React + tRPC + MySQL 架构中重新实现并扩展安全、AI 与评测能力。

## 原项目如何构建

该项目是一个经典的前后端分离 MERN 应用：`Client/` 是 Create React App 前端，`Server/` 是 Express 后端，MongoDB 通过 Mongoose 持久化用户与商品数据。开发时，前端在 `Client/` 运行 `npm start`，后端在 `Server/` 运行 `nodemon server`；后端由 `server.js` 初始化 JSON 解析、CORS、数据库连接，并将用户与商品 API 分别挂载到 `/api/users` 和 `/api/products`。

前端入口 `Client/src/App.js` 以 `BrowserRouter` 管理访问路径：落地页、注册、登录、商品首页、商品详情、发布商品、编辑商品和用户主页构成主要用户流。认证状态由 `AuthProvider` 保存到浏览器 `localStorage`，登录后页面可据此决定是否展示登录态 UI。商品控制器通过 Mongoose 直接完成创建、查询、编辑、删除、图片和规格字段变更，以及 `unsold/sold` 状态切换。

```text
浏览器
  └─ React Router 页面
      └─ fetch /api/users 或 /api/products
          └─ Express 路由与控制器
              └─ Mongoose
                  └─ MongoDB
```

## 可以借鉴的概念

| 原项目概念 | CampusMate 中的保留方式 |
|---|---|
| 面向校园的二手商品发布与浏览 | 保留为商品目录、分类筛选、搜索与商品详情。 |
| 登录后发布与编辑商品 | 改造为 Manus OAuth 登录后的角色敏感操作；管理员负责演示商品上下架。 |
| 商品规格、状态和卖家信息 | 改造成关系型商品、分类与状态字段；图片 URL 由对象存储管理。 |
| 商品详情与“确认购买”交互 | 改造成真实的**模拟订单**创建与个人订单页，而非仅改变商品状态。 |

## 必须重构的风险点

| 参考实现 | 风险 | CampusMate 的替代设计 |
|---|---|---|
| 前端将用户对象写入 `localStorage` | 可被篡改，不能作为服务端权限依据。 | Manus OAuth 会话由服务端解析，所有受保护过程使用 `ctx.user`。 |
| 商品控制器按 URL 中的 ID 直接更新或删除 | 未看到所有权/角色校验，存在越权改写风险。 | 每个管理和订单过程都在服务端检查角色或 `order.userId === ctx.user.id`。 |
| `CORS` 默认允许 `*` | 不利于生产环境跨域控制。 | 使用同源的 tRPC API 与平台会话策略。 |
| 商品图片作为请求体字段处理 | 大图会放大请求与数据库负担。 | 文件放入对象存储，数据库只保存对象键和 URL。 |
| 无独立订单实体 | 无法实现个人订单隔离、状态流转或审计。 | 新建 `orders`、`orderItems` 和不可变 `auditLogs` 表。 |
| 没有知识库、Agent 与评测机制 | 不能证明 AI 应用工程能力。 | 增加受控知识文档、可引用问答、意图路由、工具边界和固定评测集。 |
| 没有自动化测试 | 改动后容易回归。 | 为权限拒绝、审计、RAG 引用/兜底、路由和管理员门槛编写 Vitest 测试。 |

## CampusMate 的新建构建流程

CampusMate 保持一个受控全栈进程：React 19 前端通过类型安全的 tRPC 调用 Express 服务，服务层通过 Drizzle 操作 MySQL。用户身份由 Manus OAuth 注入服务端上下文；因此，前端隐藏管理员入口只是体验层，真正的订单隔离和后台权限都在服务端二次校验。

```text
React 19 前端
  └─ tRPC 过程（类型契约）
      └─ Express 服务与 Manus OAuth 上下文
          ├─ MySQL / Drizzle：商品、模拟订单、审计、评测元数据
          ├─ 对象存储：商品图片与知识文档
          └─ 受控 LLM 调用：意图路由与基于已检索片段的回答
```

对于 AI 客服，检索和权限规则优先于模型生成：规则问答只从已处理的知识片段中选择证据；证据不足时直接转人工，不能生成无来源答案。订单工具只在当前登录用户的订单范围内查询；任何跨用户订单 ID 都会被拒绝并写入审计日志。评测面板只运行固定、可见的案例集，所有指标基于程序化规则和记录的耗时计算，避免人为美化结果。

## 面试可深挖点

1. 为什么不直接在 MERN 参考项目上继续开发？因为身份体系、订单所有权、审计、文件安全和 AI 能力都要求服务端一致的权限边界；迁移到当前模板减少了双栈拼接的安全成本。
2. 为什么“前端不显示管理员入口”仍不够？攻击者可以直接调用 API，因此 admin 权限必须由服务端 `ctx.user.role` 判断。
3. 为什么 RAG 回答不能仅依赖 Prompt？Prompt 不能替代证据门槛；必须先检索、再判定置信度、并把引用片段作为结构化结果返回。
4. 为什么订单要独立为表？它需要保留商品快照、下单用户、状态与审计信息；仅把商品改成 `sold` 无法证明购买者、无法隔离访问，也无法复盘异常行为。
