# CampusMate 产品蓝图 v1

**状态：待用户确认后实施。**  
**目标：** 将校园二手交易、可溯源 AI 客服与安全订单隔离组织成一个可运行、可录屏、可深挖的完整项目。

> **首页主张：** 发现值得继续使用的校园好物。
>
> AI 客服不是首屏噱头，而是贯穿交易说明、商品发现与订单支持的可信服务层。每一条知识型回答都必须展示来源片段；没有证据时，系统只能转人工，不能编造答案。

## 1. 体验与视觉方向

CampusMate 采用已确认的**学院编辑风**。面向买家与访客的页面以象牙白画布、深墨紫标题、鼠尾草绿交易状态和大量有秩序的留白组织内容；`Noto Serif SC` 只用于品牌名、首页主标题与商品详情大标题，`Noto Sans SC` 用于正文、价格、表格与业务数据。这样在中文语境中既保留编辑感，也不会牺牲读取效率。

| 设计层 | 规则 | 目的 |
|---|---|---|
| 品牌色 | 深墨紫 `#2D213C`、紫灰 `#6B527A`、象牙白 `#F8F5EE`、鼠尾草绿 `#2E7D5B`、雾紫 `#EAE2F0` | 形成“可信、温和、校园感”的交易气质。 |
| 信息层级 | 大标题使用衬线中文；业务正文使用无衬线中文；价格用大号等宽数字风格。 | 让商品与交易信息快速扫描。 |
| 卡片 | 前台商品卡轻边框、极弱阴影与大圆角；后台表格使用更克制的白底密度。 | 同一品牌下区分“发现”与“管理”。 |
| 动效 | 商品列表进入、筛选更新和客服状态使用 160–260ms 的 transform/opacity 过渡；启用 `prefers-reduced-motion` 时静态呈现。 | 让反馈清晰，不以动画取代信息。 |
| 禁止项 | 不使用假用户评论、虚构评分、伪造成交量或“某同学推荐”等社交证明。 | 保持作品集展示真实、合规、可解释。 |

## 2. 路由与用户旅程

| 路由 | 是否登录 | 面向谁 | 页面目标 |
|---|---:|---|---|
| `/` | 否 | 所有人 | 发现好物：首页搜索、分类、精选演示商品、平台规则入口。 |
| `/goods` | 否 | 所有人 | 商品列表：关键词搜索、分类/状态筛选、清晰空状态。 |
| `/goods/:id` | 否 | 所有人 | 商品详情：图片、价格、描述、规格、卖家校园信息、模拟下单按钮。 |
| `/assistant` | 否 | 所有人 | AI 客服：规则问答、商品检索和人工转接；订单查询要求登录。 |
| `/orders` | 是 | 普通用户/管理员 | 仅列出当前会话所属的模拟订单。 |
| `/orders/:id` | 是 | 订单拥有者/管理员 | 订单详情；非拥有者一律拒绝并记录审计。 |
| `/guide` | 否 | 面试官/访客 | 需求文档、架构图、模块说明、关键取舍与深挖 Q&A。 |
| `/evaluation` | 否 | 面试官/访客 | 固定评测集、程序化口径、最近运行结果与失败案例说明。 |
| `/admin` | 是且 admin | 管理员 | 商品上/下架、知识文档上传、处理状态、审计查看入口。 |

普通用户的导航中**完全不渲染**管理入口；服务端仍会在每个 `/admin` 相关 tRPC 过程上做 `ctx.user.role === "admin"` 检查，前端隐藏永远不是安全控制。

## 3. 业务数据模型

现有 `users` 表继续作为 OAuth 身份源。新表以 MySQL 外键与服务端查询范围共同确保关系完整性。

| 实体 | 核心字段 | 责任与约束 |
|---|---|---|
| `categories` | `id`、`name`、`slug`、`description`、`sortOrder` | 五个演示分类；用于公开筛选。 |
| `products` | `id`、`categoryId`、`title`、`description`、`priceCents`、`condition`、`status`、`sellerLabel`、`createdAt` | 只放脱敏演示商品；`status` 为 `active / reserved / archived`。 |
| `productImages` | `id`、`productId`、`storageKey`、`url`、`altText`、`sortOrder` | 图片字节放对象存储，数据库仅存引用。 |
| `orders` | `id`、`userId`、`orderCode`、`status`、`totalCents`、`createdAt` | **所有个人订单查询必须强制 `userId = ctx.user.id`。** |
| `orderItems` | `id`、`orderId`、`productId`、`titleSnapshot`、`priceCentsSnapshot`、`quantity` | 保存下单时快照，避免后续商品变更影响历史订单。 |
| `knowledgeDocuments` | `id`、`title`、`sourceType`、`storageKey`、`processingStatus`、`uploadedByUserId`、`createdAt` | 仅管理员可写入；仅存商城规则、售后政策、FAQ 等演示文档。 |
| `knowledgeChunks` | `id`、`documentId`、`chunkIndex`、`content`、`tokenVectorJson`、`sourceLabel` | 每段文本存可复现词项向量；回答引用以此为唯一来源。 |
| `auditLogs` | `id`、`actorUserId`、`action`、`resourceType`、`resourceId`、`outcome`、`reason`、`createdAt` | 记录订单访问、拒绝越权、管理员写入和客服订单工具调用；应用层只追加，不提供编辑/删除过程。 |
| `evaluationCases` | `id`、`caseType`、`question`、`expectedIntent`、`expectedOutcome`、`requiredCitationDocumentId` | 固定、版本可见的问答测试集，不由模型临时生成。 |
| `evaluationRuns` | `id`、`caseId`、`intentMatched`、`citationComplete`、`refusalCorrect`、`latencyMs`、`responseSummary`、`createdAt` | 存储运行结果，面板按记录程序化计算指标。 |

## 4. 权限矩阵

| 动作 | 访客 | 登录用户 | 管理员 | 服务端强制条件 |
|---|---:|---:|---:|---|
| 浏览商品、搜索、分类筛选 | 是 | 是 | 是 | `publicProcedure`。 |
| 查看商品详情 | 是 | 是 | 是 | `publicProcedure`。 |
| 创建模拟订单 | 否 | 是 | 是 | `protectedProcedure`；订单的 `userId` 只能来自会话。 |
| 查看订单列表 | 否 | 仅本人 | 全部演示订单 | 用户查询永远添加 `where orders.userId = ctx.user.id`。 |
| 查看指定订单 | 否 | 仅本人 | 全部演示订单 | 非本人 ID：抛出 `FORBIDDEN`、写入审计。 |
| 客服查询“我的订单” | 否 | 仅本人 | 全部演示订单 | 工具函数接受用户上下文，不接受模型提供的用户 ID。 |
| 上/下架商品 | 否 | 否 | 是 | `adminProcedure`。 |
| 上传/处理知识文档 | 否 | 否 | 是 | `adminProcedure` + 文件类型/大小白名单。 |
| 查看审计日志 | 否 | 否 | 是 | `adminProcedure`；不展示给普通用户。 |

## 5. RAG 客服与 Agent 边界

### 5.1 可复现检索链路

首版采用**词项向量 + TF-IDF + 余弦相似度**。管理员上传或预置一份商城规则、售后政策或 FAQ 文档后，服务端将其拆成带重叠的小段；对每段与用户问题使用同一中文/英文分词和向量算法。排序结果、阈值与引用片段都可在本地重跑，因此评测结果可复现。

这是真实的向量检索实现，但不是语义 Embedding。项目文档会诚实说明此设计是为了避免首版依赖额外密钥与不可控模型成本；后续升级可以将 `tokenVectorJson` 替换为经批准的 Embedding 向量服务，而不改变文档、引用、权限或评测表结构。

### 5.2 Agent 处理顺序

```text
用户消息
  └─ 结构化意图路由（规则 / 商品 / 本人订单 / 人工）
      ├─ 规则：检索知识片段 → 分数是否达到阈值？
      │     ├─ 是：仅使用片段回答 + 返回引用
      │     └─ 否：说明未覆盖 → 人工转接
      ├─ 商品：调用公开商品搜索工具 → 返回结构化商品卡
      ├─ 本人订单：先验证会话 → 仅按 ctx.user.id 查询 → 写审计日志
      └─ 人工：说明转接路径，不虚构人工已响应
```

服务端调用 LLM 时使用严格 JSON Schema 接收 `intent` 与 `confidence`；模型没有权限执行 SQL，也不能传入任意用户 ID。回答阶段会把已检索文本作为唯一可用事实；如果引用数组为空，程序不返回知识型答案。

## 6. 固定评测集与指标口径

评测面板展示的是**固定案例运行结果**，不是声称线上真实用户数据。首版计划 16 个案例：6 个规则/FAQ、3 个无匹配拒答、3 个商品检索、2 个本人订单、2 个越权订单尝试。

| 指标 | 计算规则 | 合格条件 |
|---|---|---|
| 正确率 | `意图正确且预期结果正确的案例数 / 总案例数` | 所有案例均可在代码中追溯到预期值。 |
| 引用完整性 | `要求引用且返回有效来源片段的案例数 / 要求引用的案例数` | 知识问答必须 100%；无匹配与订单工具不计入分母。 |
| 拒答正确性 | `无匹配或越权案例中正确拒绝的数量 / 该类案例总数` | 无匹配不编造，越权不泄露。 |
| 平均响应时间 | `sum(latencyMs) / 总案例数` | 以服务端测量值为准，面板明确标注测试环境。 |

## 7. 首版演示数据与内容边界

商品、订单和政策文档均为**明确标注的演示数据**，不会冒充真实交易或真实用户数据。商品将覆盖数码、教材、宿舍、运动与校园生活五类；每个商品使用合规图片、真实描述逻辑和脱敏卖家标签。不会写入或展示客户评价、客户评分、客户推荐、虚构成交量或其他伪造用户生成内容。

## 8. 关键风险与应对

| 风险 | 影响 | 首版控制方式 |
|---|---|---|
| 设计偏重但业务不完整 | 录屏看起来漂亮，面试追问无法落地。 | 每个漂亮页面对应真实 tRPC 过程、真实权限与空/错状态。 |
| 模型幻觉 | 客服回答制度外信息。 | 检索阈值、引用强制检查、无证据转人工。 |
| 仅靠前端隐藏后台 | 攻击者可直接请求后台接口。 | `adminProcedure` 与数据库范围在服务端执行。 |
| 根据订单 ID 越权访问 | 隐私泄露。 | 用户订单查询固定按会话 `userId` 过滤；拒绝写审计。 |
| 外部图片、文档导致部署问题 | 体积过大或资源失效。 | 静态资源用项目对象存储；知识文档存 S3 元数据。 |
| 评测指标失真 | 项目亮点无法被相信。 | 固定案例、源码可见预期、真实运行耗时、失败案例可展示。 |

## 9. 实施前确认点

确认本蓝图后，下一阶段将先落地关系表及核心 tRPC 过程，再实现首页、商品列表、详情、登录引导和个人订单链路。RAG、Agent 与评测会在订单权限测试通过后再接入，避免在不稳定的业务基础上叠加模型复杂度。
